Le projet

Pourquoi ce portfolio

Le portfolio présente mon parcours de BTS SIO SLAM et mes réalisations au jury de l'épreuve E5 et aux entreprises qui recrutent en alternance. Il sert aussi de dossier : chaque projet a sa page, et les annexes regroupent les cahiers, fiches et comptes rendus.

C'est aussi un projet à part entière : une application Symfony organisée en composants, dont les textes sont séparés du code, exportée en pages HTML statiques et publiée gratuitement sur GitHub Pages.

  • Montrer : des réalisations concrètes, avec ce que j'ai fait moi-même, les difficultés et ce que j'en retiens.
  • Prouver : chaque affirmation renvoie à un document (cahier des charges, fiche E5, compte rendu, capture).
  • Être facile à faire évoluer : un texte se change dans un fichier YAML, sans toucher au HTML.
  • Coûter zéro et ne présenter aucune faille côté serveur : site statique, aucun PHP ne tourne en ligne.

Architecture et code

L'architecture

Les textes (YAML) et la mise en page (gabarits Twig) sont séparés. Le contrôleur Symfony lit les textes avec le service Contenu et les passe aux gabarits. La commande app:export calcule chaque page comme si un visiteur la demandait et enregistre le HTML à la racine du dépôt. GitHub Pages publie ces fichiers.

C'est le modèle MVC : les fichiers YAML jouent le rôle du modèle (les données), les gabarits Twig la vue, PageController le contrôleur.

Le chemin d'une page

Fichier YAML (texte)  +  Gabarit Twig (mise en page)  +  Composants (briques)
                    \            |            /
                     PageController (Symfony)
                               |
                  php bin/console app:export
                               |
               index.html, pages/*.html  ->  GitHub Pages

Le contrôleur et les routes

Une méthode = une page. L'attribut #[Route] donne l'adresse ; elle reprend exactement le nom du fichier exporté. La route des projets a un paramètre {slug} : une seule méthode sert les cinq pages projet. priority: -1 la fait passer après les autres routes de pages/, pour que /pages/stage.html ne soit pas pris pour un projet.

Architecture et code

Le service Contenu (lecture des YAML)

Le service lit un fichier YAML et le garde en mémoire (cache) pour ne pas le relire. Il est injecté automatiquement dans le contrôleur par son constructeur (injection de dépendances). Un projet inconnu déclenche une erreur 404.

Lire un fichier, avec un cache

app/src/Service/Contenu.php

public function get(string $fichier): array
{
    if (!isset($this->cache[$fichier])) {
        $chemin = $this->dossierContenu.'/'.$fichier.'.yaml';
        if (!is_file($chemin)) {
            throw new \RuntimeException(sprintf('Fichier de contenu introuvable : %s', $chemin));
        }
        $this->cache[$fichier] = Yaml::parseFile($chemin);
    }

    return $this->cache[$fichier];
}

Retrouver un projet par son slug

app/src/Service/Contenu.php

public function projet(string $slug): array
{
    foreach ($this->projets() as $projet) {
        if ($projet['slug'] === $slug) {
            return $projet;
        }
    }

    throw new NotFoundHttpException(sprintf('Aucun projet "%s" dans contenu/projets.yaml', $slug));
}

La configuration et l'injection de dépendances

autowire : Symfony fournit tout seul les objets demandés dans les constructeurs. bind : les paramètres $dossierContenu et $dossierExport reçoivent les chemins définis une seule fois. autoconfigure : la commande et l'extension Twig sont reconnues sans rien déclarer.

config/services.yaml

app/config/services.yaml

parameters:
    # Dossier des fichiers de contenu (textes du site, au format YAML).
    app.dossier_contenu: '%kernel.project_dir%/contenu'
    # Dossier où l'export écrit les pages HTML : la racine du dépôt, servie par GitHub Pages.
    app.dossier_export: '%kernel.project_dir%/..'

services:
    _defaults:
        autowire: true      # les dépendances sont injectées automatiquement
        autoconfigure: true # les commandes, extensions Twig, etc. sont reconnues automatiquement
        bind:
            $dossierContenu: '%app.dossier_contenu%'
            $dossierExport: '%app.dossier_export%'

    App\:
        resource: '../src/'
        exclude:
            - '../src/Kernel.php'

Architecture et code

La commande d'export

GitHub Pages ne sait pas exécuter de PHP. La commande joue chaque requête dans Symfony, sans serveur web, et enregistre le HTML. La liste des adresses est déduite des routes : ajouter une route suffit pour qu'elle soit exportée ; la route {slug} donne une page par projet.

Calculer et enregistrer chaque page

app/src/Command/ExportCommand.php

foreach ($this->adressesAExporter() as $adresse) {
    // On "joue" la requête dans Symfony, sans serveur web
    $reponse = $this->kernel->handle(Request::create($adresse), HttpKernelInterface::MAIN_REQUEST, false);

    if ($reponse->getStatusCode() !== 200) {
        $io->error(sprintf('%s : erreur %d', $adresse, $reponse->getStatusCode()));
        ++$erreurs;
        continue;
    }

    $fichier = $this->dossierExport.$adresse;
    if (!is_dir(dirname($fichier))) {
        mkdir(dirname($fichier), 0777, true);
    }
    file_put_contents($fichier, $reponse->getContent());
    $io->writeln(sprintf('  <info>ok</info>  %s', ltrim($adresse, '/')));
}

Les adresses viennent des routes

app/src/Command/ExportCommand.php

foreach ($this->router->getRouteCollection() as $nom => $route) {
    $chemin = $route->getPath();
    if ($nom === 'accueil_racine' || str_starts_with($nom, '_')) {
        continue; // "/" est un doublon de /index.html ; les routes internes de Symfony sont ignorées
    }

    if (str_contains($chemin, '{slug}')) {
        // Route des projets : une page par projet de contenu/projets.yaml
        foreach ($this->contenu->projets() as $projet) {
            $adresses[] = str_replace('{slug}', $projet['slug'], $chemin);
        }
        continue;
    }
    $adresses[] = $chemin;
}

Architecture et code

L'extension Twig lien()

Les pages sont des fichiers : les liens doivent être relatifs, et ils ne s'écrivent pas pareil depuis index.html et depuis pages/. On écrit toujours le chemin depuis la racine ; lien() le convertit. Les adresses externes et les ancres ne changent pas.

La conversion

app/src/Twig/LienExtension.php

public function lien(string $cible): string
{
    // Adresse externe ou ancre : rien à changer
    if (preg_match('~^(https?:|mailto:|tel:|#)~', $cible)) {
        return $cible;
    }

    if (!$this->estDansPages()) {
        return $cible;
    }

    // On est dans pages/ : une autre page du même dossier, ou on remonte d'un cran
    return str_starts_with($cible, 'pages/') ? substr($cible, strlen('pages/')) : '../'.$cible;
}

Utilisation dans un gabarit

{{ lien('assets/cv/CV.pdf') }}
{# depuis index.html    -> assets/cv/CV.pdf     #}
{# depuis pages/cv.html -> ../assets/cv/CV.pdf  #}

Les composants Twig

Un composant est une brique appelée comme une balise HTML. Ses paramètres sont déclarés par {% props %}. Le « : » devant un paramètre signifie « variable Twig » ; sans « : », c'est un texte. EnTete est un composant avec classe : la classe PHP prépare les liens du menu, le gabarit les affiche.

<twig:Panneau id="contexte" titre="Le contexte">
  <p>Texte libre à l'intérieur.</p>
</twig:Panneau>

Un composant avec classe : le menu

app/src/Twig/Components/EnTete.php

#[AsTwigComponent]
class EnTete
{
    /** true sur l'accueil : les liens pointent vers les sections de la page (#parcours...) */
    public bool $accueil = false;

    /** Texte du lien à mettre en surbrillance, ex. "Projets" */
    public string $actif = '';

    public function __construct(private Contenu $contenu)
    {
    }

    /**
     * Liens du menu principal (écran large).
     * Chaque lien : ['texte' => ..., 'cible' => ...]. La cible est écrite depuis
     * la racine du site ; le gabarit la passe dans lien() pour la rendre relative.
     */
    public function liens(): array
    {
        $profil = $this->contenu->get('profil');

        if ($this->accueil) {
            return array_map(
                fn (array $l) => ['texte' => $l['texte'], 'cible' => '#'.$l['ancre']],
                $profil['menu_accueil']
            );
        }

        return $profil['menu_pages'];
    }
}

var simple = function (s) { return (s || '').normalize('NFD').replace(/[̀-ͯ]/g, '').toLowerCase(); };

var mots = simple(input.value).split(/\s+/).filter(Boolean);
if (!mots.length) {
  resultats = entrees.filter(function (e) { return e.s === 'Projet' || e.s === 'Document'; });
} else {
  resultats = entrees.filter(function (e) { return mots.every(function (m) { return e._tout.indexOf(m) !== -1; }); })
    .sort(function (a, b) { return (b._t.indexOf(mots[0]) !== -1) - (a._t.indexOf(mots[0]) !== -1); });
}

Qualité, sécurité et mise en ligne

Sécurité et RGPD

  • Aucun code serveur en ligne : le site est statique, il n'y a ni PHP, ni base, ni formulaire à attaquer.
  • Échappement : Twig échappe tout par défaut (protection contre le XSS) ; |raw seulement sur mes propres textes.
  • Liens externes en rel="noopener noreferrer" : la page ouverte ne peut pas contrôler l'onglet d'origine.
  • HTTPS fourni par GitHub Pages ; aucun secret dans le dépôt.
  • Liens masqués : l'adresse de Pla'Net (outil interne de l'école) est encodée et décodée au clic, pour ne pas être indexée.
  • RGPD : pas de cookie, pas de mesure d'audience, pas de formulaire ; le localStorage ne garde que le choix du thème. Les polices viennent de Google Fonts, ce qui transmet l'adresse IP du visiteur à Google : les héberger sur le site serait une amélioration. Une page de mentions légales indique l'éditeur et l'hébergeur.

Mots-clés : sécurité RGPD XSS échappement noopener HTTPS données personnelles cookies mentions légales secret

Performance et référencement

  • Images en WebP avec une version JPG de secours (balise picture), chargées en différé (loading="lazy"), avec leurs dimensions pour éviter les sauts de mise en page.

  • Pour chaque page : un titre, une description, une adresse canonique et des balises Open Graph (aperçu quand on partage le lien) ; un sitemap.xml ; un seul h1 par page.

Organisation et évolution

Les difficultés et leurs solutions

  • GitHub Pages n'exécute pas de PHP : la commande app:export génère des pages HTML à partir de l'application Symfony.
  • Des liens qui marchent partout (en ligne comme en ouvrant le fichier) : la fonction Twig lien() calcule les liens relatifs.
  • Conflit de routes : /pages/stage.html était pris pour un projet « stage » ; priority: -1 sur la route des projets.
  • Flash sombre au chargement en mode clair : le thème est remis par un petit script placé dans le head, avant l'affichage.
  • YAML qui casse sur une apostrophe : la règle de l'apostrophe doublée, rappelée dans le guide.
  • Du HTML répété partout dans la première version : découpage en composants Twig.

Mots-clés : difficultés problèmes solutions bug liens relatifs PHP GitHub Pages apostrophe route conflit flash

Organisation et évolution

Les évolutions possibles

  • Intégration continue avec GitHub Actions : à chaque push, lancer app:export et les tests, et ne publier que si tout passe. C'est la suite logique de mon objectif DevOps.
  • Compiler Tailwind au lieu de le charger depuis un CDN, et héberger les polices sur le site (plus rapide, et plus rien n'est envoyé à Google).
  • Une version anglaise du site.
  • Mettre en ligne la gestion de cabinet une fois développée (compétence « présence en ligne »).

Mots-clés : évolutions améliorations CI CD GitHub Actions intégration continue Tailwind polices
